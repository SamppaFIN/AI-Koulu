Käyttöliittymän arkkitehtuuri ratkaisee, missä HTML syntyy, kuinka paljon JavaScriptiä selain lataa ja miten ulkoasu ja tila pysyvät hallinnassa, kun sovellus kasvaa. Tässä luvussa käsitellään viisi päätöstä, jotka vaikuttavat suoraan suorituskykyyn (luku 5) ja saavutettavuuteen (luku 4).

## 6.1 Missä HTML syntyy

| Tapa | Milloin HTML tehdään | Hyvä | Haitta |
|---|---|---|---|
| Staattinen generointi (SSG) | Buildissa | Nopein tarjoilla, toimii CDN:stä | Sisältö päivittyy vasta uudessa buildissa |
| Palvelinrenderöinti (SSR) | Jokaisella pyynnöllä | Ajantasainen ja käyttäjäkohtainen sisältö | Palvelin tarvitaan, viive kasvaa |
| Selainrenderöinti (CSR) | Selaimessa JavaScriptillä | Rikas vuorovaikutus ilman sivunlatauksia | Tyhjä sivu ennen JavaScriptin latausta, LCP kärsii |

Kun SSG- tai SSR-sivulla on vuorovaikutteinen komponentti, selain lataa komponentin JavaScriptin ja liittää sen valmiiseen HTML:ään. Tätä kutsutaan **hydraatioksi**. Jos koko sivu hydratoidaan, selain lataa ja suorittaa koodin myös osille, jotka eivät koskaan muutu.

## 6.2 Saarekearkkitehtuuri

**Saarekearkkitehtuurissa** valtaosa sivusta renderöidään staattiseksi HTML:ksi, ja JavaScriptiä ladataan vain vuorovaikutteisille "saarekkeille". Termin "component island" otti käyttöön Etsyn frontend-arkkitehti Katie Sylor-Miller vuonna 2019, ja Preactin tekijä Jason Miller kuvasi mallin laajemmin vuonna 2020 <Reference id="astro-islands" />.

Tämä sivusto on rakennettu Astrolla, joka renderöi jokaisen komponentin oletuksena HTML:ksi ja CSS:ksi ilman JavaScriptiä. Komponentista tulee vuorovaikutteinen vasta `client:*`-direktiivillä <Reference id="astro-islands" />:

```astro
<TokenizerDemo client:visible />  <!-- ladataan, kun demo tulee näkyviin -->
<Uutiskirje client:idle />        <!-- esimerkki: ladataan, kun selain on joutilas -->
```

Tämän sivuston demot ja visat käyttävät `client:visible`-direktiiviä. Teksti, taulukot ja kaaviot ovat pelkkää HTML:ää, ja vain demot ja visat ladataan Reactina. Siksi pitkä luku ei kuormita pääsäiettä (luku 5).

## 6.3 Komponentit ja koostaminen

Komponentti kapseloi rakenteen, tyylin ja toiminnan yhteen nimettyyn osaan. Kun komponentilla on paljon vaihtoehtoisia ominaisuuksia (props), siitä tulee vaikea muuttaa. Koostaminen pitää osat pieninä:

```tsx
// Jäykkä: jokainen uusi tarve on uusi prop
<Card title="Otsikko" image="/k.jpg" actions={[…]} footer={…} />

// Koostettu: käyttäjä päättää rakenteen
<Card>
  <Card.Image src="/k.jpg" alt="…" />
  <Card.Body><h3>Otsikko</h3><p>Kuvaus</p></Card.Body>
  <Card.Actions><button>Lue lisää</button></Card.Actions>
</Card>
```

**Headless-komponentti** toteuttaa toiminnan ja saavutettavuuden, kuten näppäimistökäytön, fokuksen hallinnan ja ARIA-tilat, mutta jättää ulkoasun käyttäjälle. Valikko, välilehdet ja yhdistelmäkenttä ovat vaikeita tehdä saavutettaviksi itse, joten niihin kannattaa käyttää testattua toteutusta tai natiivia elementtiä, kuten `<dialog>` (luku 3).

## 6.4 Design tokenit

**Design token** on nimetty arvo, kuten väri, väli tai fonttikoko, jota sekä suunnittelutyökalu että koodi käyttävät. Design Tokens Community Groupin muodon ensimmäinen vakaa versio 2025.10 julkaistiin lokakuussa 2025. Tokenit ovat JSON-tiedostoja, joissa jokaisella tokenilla on `$value` ja tyyppi `$type`, ja toiseen tokeniin viitataan aaltosuluilla <Reference id="design-tokens" />:

```json
{
  "color": {
    "$type": "color",
    "brand": { "$value": "#1d4ed8" },
    "link":  { "$value": "{color.brand}" }
  }
}
```

Viittaukset tekevät tokeneista kerroksellisia: perusarvot (sininen 700) ja niiden käyttötarkoitukset (linkin väri). Kun brändiväri muuttuu, muutos tehdään yhteen paikkaan, ja käyttötarkoitukset seuraavat. Kontrasti tarkistetaan käyttötarkoitusten pareille, kuten linkki taustaa vasten (luku 2).

## 6.5 Tilan kolme lajia

| Laji | Esimerkki | Missä se kuuluu pitää |
|---|---|---|
| Palvelimen tila | Tilaukset, käyttäjät | Palvelimella; selaimessa vain välimuistina, jolla on vanhenemisaika |
| Käyttöliittymän tila | Valikko auki, valittu välilehti | Lähimmässä komponentissa, joka sitä tarvitsee |
| URL-tila | Hakusana, suodattimet, sivunumero | Osoitteessa, jolloin näkymän voi jakaa ja kirjanmerkitä ja selaimen Takaisin-painike toimii |

Yleinen virhe on kopioida palvelimen data globaaliin asiakastilaan, jolloin kopio vanhenee eikä kukaan tiedä, kumpi on oikein. Toinen on pitää suodattimet vain muistissa, jolloin sivun päivitys tai jaettu linkki hukkaa ne.

## 6.6 Container queryt

Mediakysely muuttaa tyyliä näkymän leveyden mukaan. **Container query** muuttaa sitä komponentin säiliön koon mukaan, joten sama kortti voi olla kapea sivupalkissa ja leveä pääalueella ilman näkymäkohtaisia sääntöjä <Reference id="mdn-container-queries" />:

```css
.kortit { container-type: inline-size; }

@container (width > 40rem) {
  .kortti { display: grid; grid-template-columns: 12rem 1fr; }
}
```

Säiliö määritellään `container-type`-ominaisuudella, ja arvo `inline-size` sallii kyselyt säiliön leveyden perusteella <Reference id="mdn-container-queries" />.

## Sudenkuopat

- **Koko sivu selainrenderöitynä.** Sisältösivulla tyhjä HTML ja suuri JavaScript-paketti heikentävät LCP:tä ja INP:tä.
- **Kaikki hydratoidaan.** Lataa JavaScriptiä vain komponenteille, jotka sitä tarvitsevat.
- **Itse tehty valikko tai yhdistelmäkenttä.** Saavutettavuus jää helposti puolitiehen. Käytä natiivia elementtiä tai testattua headless-toteutusta.
- **Palvelimen data kopioituna globaaliin tilaan.** Kopio vanhenee. Pidä palvelin totuuden lähteenä.
